# 演示流程的真实消息触发审计

审计日期：2026-10-31。结论：当前可以由项目内真实聊天消息启动部分流程，但六步演示尚不能全部依靠消息自然衔接。点击“演示步骤”成功，不等于对应消息入口、数据来源及调度已经具备。这里的“真实消息”指 `/api/groups/{gid}/messages` 和同一聊天服务中的用户消息；仓库未提供微信等外部聊天平台的接入。

## 识别与回复改造后的更新

本次更新增加任意位置显式 @/＠（含旧名称兼容），并排除引用、转发和代码中的称呼。明确的高置信度请求不再受固定礼貌用语白名单限制；挂号支持“预定/预订/订号/排门诊”，未被快速规则覆盖的表述可按语义场景路由。查询与办理分别标识，患者/科室等信息不齐全时追问。

下文P0“急症被预后追问抢占”及P1“普通提醒被预后接管”已在消息分发层修复，并增加回归用例：急症规则优先；明确单次提醒走现有提醒执行通道。其余数据贯通、周报入口、就诊材料导入和纯文字确认的缺口仍保留，不因提示词优化而视为已经实现。

## 已完成的医院改造

- `/hospital/` 提供两家医院选择；各院使用 `/hospital/apps/{hospital_id}/` 独立入口、名称、科室及号源、按院保存的草稿和会话任务信息。
- `/api/hospital/apps/{hospital_id}/` 按院过滤状态和预约，后端拒绝跨院创建、读取、支付、取消和病历查询。旧支付链接能跳回原医院。
- 聊天挂号先推送医院选择卡；明确指定医院时直接采用。选择后只在该院查询和办理，无该科室时不静默换医院。工具缺医院选择时返回 `awaiting_hospital_selection`。
- 浏览器的全部点击经过同一节流入口，间隔至少1.5秒；挂号 skill 和演示步骤提示同步更新。

## 六步流程逐项结论

| 演示环节 | 真实消息/事件可否触发 | 当前条件与限制 |
| --- | --- | --- |
| 妈妈说膝盖不舒服 | 可以 | 群1中 mom/dad 的消息命中症状词和科室映射后产生关怀卡，无须 @；同一成员2小时冷却。不是任意家庭、群、表达方式都支持。 |
| 一句话挂号 | 可以 | 消息命中挂号/查询规则，读取档案补槽位，选择医院卡后进入该院自动化。支付是用户在收银台操作，不由文本“已支付”替代回调。 |
| 看完病→守护计划 | 部分 | “我看完门诊了”没有直接完成就诊/同步病历入口；演示按钮调用 `complete_visit`，可能补造模拟预约、快进时钟并生成模板病历。用户明确要求按病历/药单提醒时，另一条 prognosis 路径可以解析可见医嘱并发待确认卡，但依赖模型和可识别来源。单独上传图片或一句“看完了”不保证产生计划。 |
| 爸爸用药周报 | 不完整 | `adherence_report` 只有演示 week 步骤显式调用，没有周报消息分发或固定周调度。通用模型可以读 `family_health` 返回概况，不能直接执行周报卡服务。 |
| 复诊前一天简报 | 有条件 | `care.tick` 会在 `care_item` 复诊事项到达 `briefing_at` 时生成；需要先存在该记录。真实药单提醒确认只写 `reminder`，没有生成这种 `care_item`，因此那条路径不能自动衔接简报。 |
| 爸爸突发胸痛 | 通常可以，存在优先级缺陷 | 普通消息会命中规则并发急症卡；但若该成员正在预后追问状态，prognosis 先于急症处理，可能抢占消息，见下面P0问题。 |

## 原因与解决方案

### P0：急症规则可能被预后追问抢占

`Agent.process` 先调用 `prognosis.handle_request`，再调用 `care.on_message`。预后模块的 `continuing` 在1小时内可使任何新消息进入模型；一旦返回 True，后面的红旗规则就不执行。隔离复现：给爸爸设置待补充的预后请求，再发送“胸口疼得厉害，有点喘不上气”，结果调用预后模型、没有 emergency 卡。没有该 pending 状态时相同消息会产生 emergency 卡。

解决：把确定性急症检查放到所有模型、追问续接和普通意图之前；明确取消/转话题时结束预后 pending。增加“预后追问中出现急症仍优先走急症”的端到端回归测试。该项已在后续识别改造中按上述顺序修复。

### P1：演示事件与真实消息入口不等价

`run_step` 中 hint/booking/emergency 通过 `post_as` 写入 `Message` 和 pending job，与普通发消息管线基本相同；visit/week/followup 则直接调用业务函数、调整演示时钟、补齐模拟记录，部分场景还自动确认计划。真实聊天入口没有这些额外动作。

解决：新增基于消息来源的就诊材料导入/就诊完成服务，缺材料时追问；周报提供只读消息工具和去重周调度；演示按钮只调用这些公共服务并显式标记模拟输入。不要把聊天“看完病了”直接映射到会补造预约/医嘱的 `complete_visit`。

### P1：真实提醒与演示照护数据不贯通

`prognosis.activate` 创建逐次 `reminder`；`confirm_plan_items` 创建 `care_item` 和医疗档案；打卡、依从性和复诊简报读取后者。两套计划卡长得相似，确认后的实际能力不同。真实药单的提醒可以投递，但不会自然产生康复打卡和复诊简报。`simulate` 补齐的记录含 `by=simulated`，也不能视作家人真实服药证据。

解决：统一有来源、患者、事项ID和确认状态的照护计划。计划确认后同时创建提醒 occurrence 和可打卡事项；记录真实确认、未确认、取消，保留模拟来源。周报按真实日志统计，不把未打卡写成已服或必然漏服；复诊事项共享同一计划与来源。

### P1：预后路由过宽、普通提醒会被误接管

“十分钟后提醒爸爸吃药”同时命中“提醒”和“吃药”，进入病历解析，而不是既有普通提醒命令。隔离测试确认它调用了预后模型，固定返回补材料问题，没有创建普通提醒。这会让简单提醒也依赖病历和模型。

解决：区分“明确时间+普通提醒”和“按医嘱生成多项守护计划”。先解析明确普通提醒；只有明确请求医嘱守护或可见医嘱材料相关的续接才进入预后流程。pending 只接受与缺失槽位相关的回复，不能吞掉所有消息。

### P1：纯文字确认与卡片动作不是同一个入口

当前医院选择、计划确认、付款依靠对应卡片/收银台动作。“选第二家”“确认计划”没有统一 pending 挂号续接分发；通用模型回复不代表业务已执行。付款本来就应继续保留本人收银台确认。

解决：为非支付选择建立绑定用户、空间、原始请求、候选项和版本的待办状态，消息与卡片复用同一验证服务。识别到明确选择才执行；重复、失效、跨用户的确认不重复执行。付款继续以实际收银台结果为准。

### P2：适用范围、失败恢复与模型能力限制

- 快速就医通道硬编码群1和 mom/dad/child；日常表达依赖正则，不等于通用语义覆盖。应改为会话成员角色与档案驱动，并提供可追问的意图抽取。
- 真实识图把最近人类消息的图片作为 `image_url` 发给通用模型，没有独立 OCR/视觉能力探测。应配置可验证的视觉模型或 OCR，明确失败原因；病历原文、识别置信信息和原附件保持可追溯。当前验证未证明线上模型识图准确率。
- `care.tick` 只在每日事项到点后15分钟窗口内发卡，重启错过窗口会漏提醒；复诊事项在生成简报前先标 `briefing_sent=True`，异常时缺少自动重试。应使用持久化投递状态、补发窗口和成功后确认。
- 演示时钟快进会调用 `simulate` 补造打卡。真实流程应使用真实调度及日志，快进和模拟记录保持独立。

## 验证方法与实际观察

1. 浏览器实测两家独立应用：选择入口、单院科室页面、按院草稿保存；再通过真实聊天 REST 发送挂号请求，点击选择对应医院，等待自动锁号并在所属应用确认模拟支付。两院均成功，另一院 API 不展示该订单，浏览器无运行错误。
2. 后端回归覆盖按院状态过滤、跨院创建/读取/支付/取消/病历拒绝、未知应用、任务标识按医院区分、无医院不启动自动化、1.5秒点击间隔。
3. 使用真实 REST 消息入口加实际 `Agent.process`，在隔离数据库和固定模型返回下验证路由：不适→need_hint，挂号→hospital_apps，普通急症→emergency；就诊完成和周报消息没有直接业务卡；普通吃药提醒及“预后待追问+急症”进入 prognosis。固定模型用于确认服务器分发，不证明任意自然语言或线上视觉模型的效果。

建议落地顺序：急症优先级 → 普通提醒与预后意图区分 → 统一照护计划数据 → 真实就诊材料入口与周报工具/调度 → 文本选择续接及投递恢复。不要通过让 skill 描述得更强来替代缺少的工具、服务和状态机。
